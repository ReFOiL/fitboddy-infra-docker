# Fitboddy: платежи и выплаты — выбранный контур

Версия: 1.1  
Дата: 2026-08-15  
Связанные документы: `BILLING_DESIGN.md`, `BUSINESS_PLAN.md`, `TECH_SPEC.md`, `PAYMENTS_ACCOUNTING_REVIEW.md` (текст для сверки с бухгалтером).

Это операционный каркас для основателя-разработчика, не юридическая консультация и не текст договоров. Перед первым боевым платежом схему и оферты проверяет юрист + бухгалтер.

---

## 1. Выбранная схема

Два продукта, две сделки, один эквайер. Не смешивать в одном платеже и одном чеке.

**Продукт 1. Свои тренировки Fitboddy (ориентир 500 ₽/мес)**

- Продавец — платформа. Это наша реализация.
- Вся сумма минус эквайринг — наша выручка.
- Сплит и выплат нет. Чек от Fitboddy за 500 ₽ — правильный.
- Открывает system-plan (план без тренера). Не открывает контур чужого тренера.

**Продукт 2. Подписка на тренера**

- Продавец — тренер. Платформа — агент.
- Сплит у ЮKassa: комиссия нам, остальное тренеру.
- Выручка платформы = `platform_fee`. `trainer_payout` — не наш доход.
- Тренер получает выплату только как самозанятый или ИП.
- Открывает платный контур этого тренера. Не заменяет оплату своего тарифа и наоборот.

Пока нет ИП и договора с ЮKassa — только sandbox. Код биллинга от этого не зависит.

Почему продукт 2 не делаем как «все деньги нам»:

- совпадает с тем, что цену ставит тренер;
- налог с комиссии, не со всего платежа тренеру;
- претензия по качеству тренера не делает нас продавцом его услуги;
- не нужно долго держать чужие деньги.

## 2. Кто есть кто

| Роль | Кто | Что делает |
|---|---|---|
| Продавец своего тарифа | Fitboddy | продаёт system-plan, ~500 ₽, чек от себя |
| Принципал | тренер | продаёт доступ к себе, получает `trainer_payout` |
| Агент | Fitboddy (ИП основателя на старте) | витрина, checkout тренера, комиссия |
| Плательщик | клиент | платит картой за один из двух продуктов |
| Эквайер | ЮKassa | карта, чек; для продукта 2 ещё сплит и выплата |
| Получатель выплаты | тренер как самозанятый или ИП | только продукт 2; не «просто физлицо» |

Клиенту деньги возвращаются только при refund. В разговорах не называть выплату тренеру «выплатой клиенту».

## 3. Как едут деньги

Свой тариф, пример `500 ₽`, эквайринг на платформе:

```
клиент платит 500 ₽
        │
        ▼
     ЮKassa
        │
        └── 490 ₽  → расчётный счёт Fitboddy     (вся сумма минус эквайринг)
```

Подписка тренера, пример `2500 ₽`, `take_rate = 15%`, эквайринг на тренере:

```
клиент платит 2500 ₽
        │
        ▼
     ЮKassa
        │
        ├── 375 ₽  → расчётный счёт Fitboddy     (platform_fee, наша выручка)
        └── 2075 ₽ → самозанятому / ИП тренера   (минус комиссия эквайера)
```

В ledger это уже описано в `BILLING_DESIGN.md`:

```
gross_minor = platform_fee_minor + processor_fee_minor + trainer_payout_minor
```

Юридический смысл тех же цифр:

- у своего тарифа: `seller_type = platform`, `trainer_payout_minor = 0`, `platform_fee_minor = gross_minor - processor_fee_minor` (эквайринг наш);
- у тарифа тренера: `seller_type = trainer`, `gross_minor` — платёж тренеру, `platform_fee_minor` — агентское, `processor_fee_minor` — на тренере, `trainer_payout_minor` — доля тренера.

В офертах это должно быть двумя разными формулировками, не одной «подпиской Fitboddy».

---

## 4. Почему не другие схемы

**Всё на наш счёт, потом сами платим тренерам.**  
Проще в коде на неделю. Дальше: чужой оборот на счёте, соблазн провести его как выручку, ручные платежи, спор «где мои деньги». Допустимо только как короткий костыль пилота, см. §7.

**Мы продавец и по тарифу тренера (MoR на всё).**  
Нормально только для своих 500 ₽. На 2500 ₽ тренера — налог и претензии с полного чека, ломает «тренер сам ставит цену».

**Клиент платит тренеру напрямую, мы выставляем счёт на комиссию.**  
Юридически спокойно для нас. Операционно плохо: доступ уже открыт, комиссию тренер может не заплатить.

**Stripe.**  
Не основной путь для пилота в РФ и рублях. Запасной контур, если юрлицо и клиенты окажутся не в РФ.

## 5. Что открыть до первого боевого платежа

Порядок такой. Код billing P0 можно писать параллельно, боевой ключ ЮKassa — только после пунктов ниже.

1. **ИП** на основателя. ООО на старте не нужно: дольше, дороже, тот же эквайринг. ООО имеет смысл позже, когда появятся партнёры, найм или желание отделить личную ответственность.
2. **Расчётный счёт ИП** в любом банке, который нормально живёт с ЮKassa.
3. **Бухгалтер** (хотя бы исходящий): УСН «доходы» обычно достаточно, если нет НДС-схем. Доход платформы = свои 500 ₽ + комиссия с тренера, не весь платёж тренеру.
4. **Договор с ЮKassa** на интернет-эквайринг + сплит / выплаты самозанятым. Если сплит молодому ИП не дадут сразу — не запускаем публичный приём, идём в костыль §7 или ждём подключение.
5. **Тексты**, которые пишет юрист по этому каркасу:
   - оферта клиента: отдельно свой тариф Fitboddy и подписка на тренера;
   - агентский договор / оферта тренера (комиссия, эквайринг, выплаты, статус самозанятого/ИП);
   - политика возвратов;
   - пользовательское соглашение и обработка ПДн, если ещё не закрыты.
6. **Онлайн-чек (54-ФЗ).** На старте чек отправляет ЮKassa. Два шаблона: свои 500 ₽ — реализация Fitboddy; 2500 ₽ тренера — не наша реализация на полную сумму. Как ЮKassa указывает принципала — фиксирует юрист при подключении.

ОКВЭД подбирает бухгалтер. Ориентир, не инструкция к регистрации: разработка ПО + информационные услуги / деятельность агентов. Не ставить «банковские услуги» и не писать в анкете ЮKassa, что мы выдаём займы.

## 6. Тренер: кого пускаем к деньгам

Без статуса выплата на карту физлица делает нас налоговым агентом (НДФЛ, взносы, отчётность на каждого человека). Для маркетплейса это не взлетает.

Правило продукта:

- зарегистрироваться и завести оффер можно без статуса;
- **получить выплату и, на боевом контуре, принять оплату нельзя**, пока нет самозанятости или ИП.

Что собираем у тренера перед первой выплатой:

- ФИО, ИНН;
- статус: самозанятый или ИП;
- реквизиты, которые просит ЮKassa (карта / счёт / кошелёк провайдера);
- акцепт агентской оферты.

Самозанятый — основной путь: открывается в «Мой налог» за вечер, налог 4–6%, чек дохода либо сам, либо через интеграцию провайдера. ИП тренера тоже ок, онбординг тяжелее.

В коде это поле статуса и блок выплаты, не «просто строка карты». Пока статуса нет — в UI честно: «оплату клиентов включим после подтверждения самозанятости / ИП».

## 7. Этапы, без прыжка в сложность

### Этап 0 — сейчас

Sandbox в `billing-service`. Ledger считает начисления. Живых денег нет. Юрлицо не блокирует разработку P0.

### Этап 1 — первый боевой пилот

ИП + ЮKassa + сплит. 5–15 знакомых тренеров, все самозанятые. Возвраты руками через кабинет ЮKassa, не автоматом в продукте.

### Этап 2 — если сплит ещё не подключили

Только с жёстким потолком, иначе это уже другая компания:

- все деньги приходят на счёт ИП;
- в учёте `trainer_payout` — задолженность принципалам, **не выручка**;
- выплата раз в неделю переводом, не когда тренер нажал кнопку;
- лимит: не больше 10 тренеров и небольшой висящий остаток (бухгалтер задаёт цифру);
- как только сплит доступен — костыль выключаем.

Если лимит упирается, а сплита нет — **останавливаем приём новых платящих**, а не пишем свой «внутренний банк».

### Этап 3 — обычная работа (биллинг P1)

Только сплит. `payouts` в сервисе — сверка и статусы «начислено / выплачено провайдером», не самостоятельная рассылка денег с нашего счёта. Отчёт тренера показывает начисления и факт выплаты от ЮKassa.

---

## 8. Возвраты

Простая политика для пилота, юрист подтверждает формулировки:

- платёж прошёл, доступ ещё не активирован (`pending` / сбой) — полный возврат;
- подписка `active` и период уже начался — без возврата за текущий месяц, кроме исключения (двойное списание, баг доступа);
- отмена — доступ до `current_period_end`, следующее списание не создаём;
- chargeback / спор банка — доступ закрываем, разбираем вручную.

Деньги при сплите возвращаются с обеих долей: наша комиссия и доля тренера. Если тренеру уже ушло, возврат либо тянет ЮKassa с его баланса, либо мы компенсируем и удерживаем из следующих начислений. Второе нужно заранее написать в оферте тренера, иначе «вычтем потом» незаконно.

В P0 автоматических refund в API нет. Кнопка админа + кабинет ЮKassa достаточно.

## 9. Что пишет юрист, чего не пишем мы

В оферте клиента обязательно два контура:

- тариф Fitboddy: услугу оказываем мы, цена ~500 ₽;
- тариф тренера: услугу оказывает тренер X, мы агент, комиссия уже внутри его цены;
- период, автопродление, как отменить — по каждому тарифу;
- цена в рублях (в API по-прежнему копейки);
- возвраты из §8.

В оферте тренера обязательно:

- агентский договор: мы принимаем деньги от его имени;
- `take_rate` и кто платит эквайринг;
- выплата только самозанятому / ИП;
- срок и способ выплаты (сплит сразу или еженедельно на костыле);
- удержание при возврате / чарджбеке;
- он отвечает за содержание тренировок и коммуникацию с клиентом.

Не делать:

- чек «Fitboddy, услуга тренировки, 2500 ₽», если продавец — тренер (для своих 500 ₽ такой чек как раз нужен);
- проводить GMV как выручку ИП «а тренерам потом»;
- принимать боевые платежи на личную карту основателя;
- копить выплаты десяткам людей без статуса;
- обещать в UI «деньги завтра на карту», если провайдер платит T+N.

## 10. Как это ложится на код

Код как в `BILLING_DESIGN.md`, плюс `seller_type`: `platform` | `trainer`.

| Этап продукта | Юрконтур | Код |
|---|---|---|
| Billing P0 | sandbox, начисления | оффер тренера, оффер платформы, checkout, webhook, ledger, access |
| Первый боевой пилот | ИП + ЮKassa + сплит | `BILLING_PROVIDER=yookassa`, те же сущности |
| Billing P1 | выплаты через провайдера | статусы payout, отчёт «начислено / выплачено» |
| Костыль §7 | деньги на ИП, ручной перевод | ledger как есть, payout `manual`, без автовыплат |

В адаптере провайдера сразу закладываем:

- `amount_minor` (копейки);
- `metadata`: `seller_type`, `trainer_user_id?`, `subscription_id`, `payment_id`;
- получателя сплита только для `seller_type = trainer`;
- `processor_fee_minor` из webhook, если ЮKassa его присылает.

Не строить свой кошелёк, баланс с выводом «когда угодно» и внутренние курсы. Это платёжная деятельность, нам она не нужна.

Онбординг тренера к выплатам — отдельный шаг после оффера: ИНН, статус, акцепт оферты, id в ЮKassa. Без этого боевой checkout этого тренера не создаём.

## 11. Чеклист запуска боевых денег

Пока любой пункт не закрыт — ключ ЮKassa не в prod.

- [ ] ИП и расчётный счёт
- [ ] Бухгалтер понимает: выручка = свои 500 ₽ + комиссия, не весь платёж тренеру
- [ ] ЮKassa подключена; для тренера сплит подтверждён (или костыль §7 с лимитом)
- [ ] Оферта клиента закрывает оба тарифа; агентская оферта тренера акцептуется в продукте
- [ ] Политика возвратов опубликована
- [ ] Чеки 54-ФЗ настроены провайдером
- [ ] Тренер без самозанятости/ИП не может принять оплату
- [ ] В учёте и в ledger `trainer_payout` не смешан с выручкой
- [ ] Секреты ЮKassa не в git, webhook только с проверкой подписи
- [ ] Юрист посмотрел этот каркас и тексты оферт

## 12. Открыто для юриста, не для кода

Эти вещи не блокируют billing P0 в sandbox. Они блокируют боевой ключ.

1. Точные формулировки: «агент» vs «информационный посредник» — как лучше для вашей налоговой и ЮKassa.
2. Как ЮKassa печатает два чека: реализация Fitboddy на 500 ₽ и агентский/принципал на платёж тренеру.
3. Нужна ли платформе регистрация как платёжный агент, если когда-то снова начнём держать деньги на своём счёте дольше суток.
4. Когда ИП пора менять на ООО.

Пока эти четыре пункта не закрыты, публичный приём карт не включаем. Разработка sandbox от них не ждёт.
